# Rendering performance research

Research date: 6 November 2026. ManimJS is a general JavaScript graphics library; topology articles are its first showcase. The browser distribution must work through one classic script tag, with an independent ES-module alternative. Renderer experiments stay outside the stable API until correctness and browser measurements justify them.

The strongest measured improvement so far comes from changing geometry representation. Caching, batching, and shader specialization are the next candidates. Neural methods remain candidates for expensive fields and compressed assets, rather than a replacement for inexpensive analytic geometry.

## Lessons from Blender and game engines

| Engine  | Primary evidence                                                                                                                                                                                                                                                                                                          | Proposed transfer                                                                                                                                       |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Blender | [Draw Manager](https://developer.blender.org/docs/features/gpu/draw_manager/) stores command headers separately from payloads, supports repeated submission, and distinguishes a simple pass from a heavier batching/culling pass.                                                                                        | Compact command data, cheap sorting of indices, and a small-scene path. GPU culling needs enough objects to amortize its setup.                         |
| Unity   | [SRP Batcher](https://docs.unity3d.com/6000.0/Documentation/Manual/SRPBatcher.html) retains material buffers and reduces state changes between draws.                                                                                                                                                                     | Group data by update frequency: frame, material, geometry, instance. Fewer draws alone is not the complete performance metric.                          |
| Unreal  | [Mesh Drawing Pipeline](https://dev.epicgames.com/documentation/en-us/unreal-engine/mesh-drawing-pipeline-in-unreal-engine) retains draw descriptions, caches commands, and explicitly tracks invalidation dependencies and resource lifetimes.                                                                           | Build draw descriptions when structure changes; keep animated values in persistent buffers. Buffer replacement must invalidate commands referencing it. |
| Godot   | [GPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html) explains batching/state reduction and lost culling granularity; [CPU rendering optimization](https://godotengine.org/article/rendering-cpu-optimizations/) demonstrates profiling both sides of CPU/GPU tradeoffs. | Batch within visible regions, not across an entire article. Measure total frame cost and allocation pressure, including bookkeeping.                    |

These are architectural lessons, not proposals to embed an editor or port its full runtime. Large render graphs, GPU scene databases, meshlets and indirect-draw machinery need workloads that justify their fixed costs. A single browser file can contain a small modular engine without inheriting those systems.

## Forums and Hacker News

Community reports are useful experiment leads, not portable benchmark results:

- The [Hacker News vector rendering discussion](https://news.ycombinator.com/item?id=46473247) raises coverage, overlap and winding issues. Future stroke/fill comparisons must include self-intersections, translucent overlaps, cusps, animated zoom and high DPI, not just attractive screenshots.
- A [Three.js forum comparison](https://discourse.threejs.org/t/webgpurenderer-2x-slower-cpu-and-5-10x-slower-first-frame-than-webglrenderer-on-many-mesh-scenes-r183-same-on-both-backends/91904) reports many-mesh CPU overhead even when switching the underlying backend. The upstream [uniform-buffer issue](https://github.com/mrdoob/three.js/issues/30560) supports investigating per-object bindings and uploads. Neither establishes that WebGL or WebGPU is universally faster.
- A [GraphicsProgramming packing discussion](https://www.reddit.com/r/GraphicsProgramming/comments/1thgxlg/how_to_balance_shader_work_vs_bandwidth/) reports a smaller vertex buffer running slower after decoding work was added. The relevant primary methodology is [NVIDIA's hardware bottleneck analysis](https://developer.nvidia.com/blog/the-peak-performance-analysis-method-for-optimizing-any-gpu-workload/): identify the limiting work before trading memory traffic for arithmetic.

## Mathematical reductions and shader experiments

For the current map, `H(x,y)=(x+a sin(3y+phase), y)`, the phase identity separates static and changing data. The per-frame uniform contains `a sin(phase)`, `a cos(phase)` and scale. No vertex coordinates need uploading.

Horizontal rows are straight and can collapse to one segment each. Vertical curves differ only by translation, so instances share one curve. For `f(y)=a sin(3y+phase)`, `|f''| <= 9|a|`; uniform segments of length `h` have linear-interpolation error at most `9|a| h²/8`. Multiplying by framebuffer pixels per world unit gives a resolution-dependent segment budget. This is a derived bound for this fixture, not a general curve simplifier. Floating-point and rasterization error remain separate.

This representation preserves the fixture's shear form and inverse, even with a piecewise-linear offset. Arbitrary curve simplification does not inherit that guarantee. [Raph Levien's flattening](https://raphlinus.github.io/graphics/curves/2019/12/23/flatten-quadbez.html) and [path simplification](https://raphlinus.github.io/curves/2023/04/18/bezpath-simplify.html) work motivates explicit error metrics and fewer segments, including cusp handling.

Next candidates, evaluated separately:

1. **Production strokes:** adaptive triangle strips versus analytic quadratic/cubic coverage. [Loop and Blinn](https://developer.nvidia.com/gpugems/gpugems3/part-iv-image-effects/chapter-25-rendering-vector-art-gpu) evaluates implicit curves in fragment shaders. Measure fragment overdraw as well as tessellation cost; test joins and transparency explicitly.
2. **Compact attributes:** normalized 16-bit coordinates/bases versus float32. Quantization gets its own screen-space error allocation, especially under zoom. Smaller buffers are not automatically faster.
3. **Low-rank bases and approximation:** precomputed Fourier/Chebyshev coefficients or lookup tables for expensive repeated functions. Compare polynomial degree, table cache behavior, setup cost and worst observed error; use certified bounds when mathematical meaning depends on them.
4. **Change tracking:** packed buffers, dirty ranges and command caches. Vary object counts, dirty fractions, material counts and visibility; do not extrapolate from a one-draw scene.
5. **Compute scheduling:** vary workgroup size, data layout and intermediate storage. [AMD](https://gpuopen.com/learn/rdna-performance-guide/) and [NVIDIA](https://developer.nvidia.com/blog/advanced-api-performance-shaders/) guidance is hardware-specific. Browser optional features require capability checks.
6. **Workers and WASM SIMD:** candidates for expensive geometry preparation. Include startup, copying/transfers, synchronization, memory and input responsiveness in the comparison. Workers do not increase the GPU's throughput by themselves.

[WGSL numerical accuracy](https://www.w3.org/TR/WGSL/#floating-point-accuracy) is part of the contract: native `sin` is not interchangeable with a correctly rounded CPU reference at arbitrarily tight tolerances.

## Neural methods

[Instant NGP](https://research.nvidia.com/publication/2022-07_instant-neural-graphics-primitives-multiresolution-hash-encoding) combines multiresolution trainable features with a small network and fused CUDA kernels. [Neural texture compression](https://research.nvidia.com/labs/rtr/neural_texture_compression/) trades stored texture data for learned decoding. [Neural shading](https://research.nvidia.com/labs/rtr/publication/duca2025neural/) discusses small networks and native cooperative-vector acceleration. Those results do not establish equivalent performance for portable WGSL/GLSL across Firefox and Chromium.

A useful ManimJS neural experiment would approximate an expensive repeatedly evaluated field, not two scalar trigonometric calls per frame. Compare an MLP or hash-grid model with a lookup texture, polynomial basis and the direct function at the same error budget. Record training/preprocessing time, weights and features, decoded bandwidth, shader compilation, inference time, worst error, derivative error and temporal stability. Tensor acceleration cannot be a baseline assumption.

An approximate break-even condition is `training + K*(feature lookup + inference) < K*direct evaluation`, subject to acceptable error and memory. For distributed pretrained assets, training is offline but download/decode cost still counts. This is a screening model, not a measured speedup. Approximate SDF zero sets or fields must not silently become the authoritative topology or picking geometry. No neural model has yet been benchmarked here.

Pressure projection is a concrete future neural candidate: [Tompson et al.](https://proceedings.mlr.press/v70/tompson17a.html) train a convolutional network for the solve. The acceptance test would require equal divergence residual and long-horizon stability against Jacobi and a classical multigrid/FFT baseline, plus inference/weight/download costs in portable browser shaders. A useful hybrid could predict an initial pressure and finish with a residual-checked numerical solve; this remains a hypothesis. [GPU Gems 3](https://developer.nvidia.com/gpugems/gpugems3/part-v-physics-simulation/chapter-30-real-time-simulation-and-rendering-3d-fluids) discusses more efficient classical pressure solvers. The current fixed-iteration fluid results show why timing without residual error is insufficient.

## Difficult workloads and distribution

The fluid experiment adds repeated velocity/dye advection, divergence, Jacobi pressure iterations, projection and a render pass. It is based on the class of methods described in [GPU Gems fluid dynamics](https://developer.nvidia.com/gpugems/gpugems/part-vi-beyond-triangles/chapter-38-fast-fluid-dynamics-simulation-gpu), with periodic boundaries and compatible backward-divergence/forward-gradient operators. It measures compute and memory behavior that thin lines cannot expose. Fixed iterations leave residual divergence; semi-Lagrangian transport is dissipative and not exactly mass conserving. Both are logged.

The fluid solver is an optional WebGPU benchmark, not part of the distributed core or a promised Firefox WebGL2 feature. The experimental grid supports both low-level backends; its packaged default is WebGL2. Default WebGPU availability varies by browser/OS according to [Mozilla's platform notes](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Experimental_features#webgpu_api). Use feature detection and report unavailable capabilities without changing hidden browser preferences.

Build outputs are self-contained `dist/manim.js` (global `ManimJS`) and `dist/manim.module.js`. Shader strings are embedded. Build metadata checks for external imports and records raw/gzip/brotli sizes. `examples/standalone.html` demonstrates the classic-script path; no npm tooling is required by its consumer. The `experimental` namespace makes the current grid fixture's status explicit while the general scene API develops.

## Evidence and next acceptance gates

- [Shared-geometry measurements](../results/experiment-002.md) distinguish exact representation changes from bounded approximation and software timing from hardware timing.
- [Experiment runs](../results/runs/) retain per-run results and telemetry. Missing GPU counters remain null. See [measurement protocol](research-plan.md) for metric definitions.
- Browser and physical-GPU execution are blocked in this environment. Native Dawn/SwiftShader, a simulated host and a successful JS build do not certify browser compatibility.
- Before promoting rendering APIs: execute the standalone HTML and both browser backends on real Chromium/Firefox; measure integrated and discrete GPUs; add production stroke coverage and context-loss recovery. Next stress scenes should vary object/material counts and visibility, then extend to triangle surfaces and text.
